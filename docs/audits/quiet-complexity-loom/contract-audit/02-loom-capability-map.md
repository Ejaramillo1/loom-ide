# 02 — Loom capability map

The [upstream reference](https://github.com/teradata-labs/loom) identifies the project. Technical findings below use the pinned local checkout, not a claim that the online default branch or the running binary matches it. The [full RPC catalogue](evidence/loom-rpc-inventory.md) lists **162 RPCs in 11 services** with request/response messages, HTTP annotations and implementation-symbol locations. Symbol presence alone is not a working implementation.

## Architecture independently established

`cmd/looms` bootstraps the Go server. `pkg/server/multi_agent.go` routes requests to registry agents, resolves session ownership, admits turns, calls `ag.Chat` or `ag.ChatWithProgress`, and records observability. `pkg/agent` executes the provider/tool conversation loop and context/memory logic. `pkg/shuttle` supplies tool execution, admission hooks and held human requests. `pkg/storage` and the configured backend own durable server records. This is a runtime independent of the IDE's JSON and markdown stores.

`pkg/server/http.go::Start` registers **LoomService** with grpc-gateway JSONPb; `/v1/weave:stream` is a separate hand-written SSE handler using Go encoding/json. Other LoomService streams use generated `runtime.ForwardResponseStream`. TaskService and SkillsImportService have generated HTTP annotations but are not registered in this HTTP bootstrap. The live board/task 404s corroborate that difference. No transport decision was invented or applied during this audit.

Supported = an inspected implementation exists. Exposed = the relevant runtime interface actually makes it reachable. Integrated = the IDE calls and consumes it correctly. Verified = an executed test or observation demonstrates the stated layer. A passing read does not verify mutation, model execution or UI rendering.

## Contracts that cannot be inferred from names

- Custom chat SSE input/output uses snake_case generated Go JSON tags. Gateway protojson uses camelCase and string-encoded int64s. Changing all requests to one convention would break a different path.
- Agent creation requires `{config: AgentConfig}`, not a bare AgentConfig. MCP Add wraps server, Test reports booleans/errors, Health uses a name-keyed map.
- Gateway stream envelopes wrap a `result` or `error`; ABTestEvent has its own event payload structure. Reaching a route is insufficient if the UI never decodes its frames.
- Tool results, model output and recorded user decisions are different forms of evidence. No existing RPC makes a generated arm reply an independently verified experiment.
- Loom does not implement a universal IDE Manual/Assisted/Collaborative/Delegated policy field or a universal pause-any-execution operation. Store-backed approval, schedule pause and connection cancellation are narrower primitives.

## Reverse direction: capabilities absent from the UI

The RPC catalogue exposes the bounded reverse inventory. Current UI omissions include graph/memory layer inspection, judge evaluation, learning, compilation, slot-scheduler inspection, bus/shared memory, artifact upload/delete, workflow-template application and Lua management. These are not permission to build eleven new dashboards. Group them under the existing work detail/context surfaces after choosing transport and defining supported human workflows. Exclude unsupported/stub methods such as persistent judge history from the completion promise.

**Measurable completion:** for each included capability, record its service registration/configuration, exact request/response schema, real UI action, authoritative identifiers, visible success/error, durable relationship, permissions and one safe live workflow. No capability is fully verified from this map alone.

## Configured gRPC registration evidence

`cmd/looms/cmd_serve.go:2610` constructs the multi-agent service and configures session ownership from auth enablement. Lines 2618–2646 register LoomService and LLMSchedulerService, conditionally register TaskService/GraphMemoryService when their stores exist, and register JudgeService. SkillsImportService is registered around line 2707 only when its importer/router prerequisites exist; learning is registered around line 3161 when configured. This establishes bootstrap conditions independently of proto annotations. It does not change the separate HTTP bootstrap, which registers only LoomService. A running service's enablement still requires its own live probe.
